# Implementation Spec: TS-04 — Create Frontend-Only Reports Page with Mock Table Data

## Story Metadata

| Field | Value |
|---|---|
| **JIRA Key** | TS-04 |
| **Title** | Create Frontend-Only Reports Page with Mock Table Data |
| **Type** | Feature |
| **Priority** | Medium |
| **Status** | Draft |

## Story Summary

As a dashboard user, I want to view a Reports page displaying a single table with hardcoded mock report data so that I can see a sample reports listing without any backend integration. The page is accessible from the dashboard sidebar and shows five columns (Report Name, Type, Generated By, Generated Date, Status) with status badges for Completed, Pending, and Failed states.

## Business Goal

Provide users with a visible Reports page accessible from the dashboard sidebar, establishing the UI foundation for a reports listing. This delivers a functional frontend-only experience that demonstrates table-based data display patterns, which can later be connected to real backend APIs.

## Functional Requirements

1. A Reports page is accessible via the "Reports" option in the dashboard sidebar navigation.
2. The Reports page is served at the route `/reports`.
3. The page displays a heading: **"Reports"**.
4. The page displays a subtitle: **"View generated analytics reports"**.
5. The page shows exactly **one table** — no charts, cards, filters, tabs, or extra widgets.
6. The table displays mock data with the following columns:
   - **Report Name**
   - **Type**
   - **Generated By**
   - **Generated Date**
   - **Status**
7. The table is populated with exactly five hardcoded mock records:

   | Report Name | Type | Generated By | Generated Date | Status |
   |---|---|---|---|---|
   | Revenue Summary | Financial | John Doe | 2026-05-01 | Completed |
   | User Activity Report | Analytics | John Doe | 2026-05-02 | Completed |
   | Page Views Report | Traffic | John Doe | 2026-05-03 | Pending |
   | Session Report | Analytics | John Doe | 2026-05-04 | Completed |
   | Transaction Report | Financial | John Doe | 2026-05-05 | Failed |

8. Status values are displayed as visually distinct badges:
   - **Completed** — green/emerald styling
   - **Pending** — amber/yellow styling
   - **Failed** — red/rose styling
9. No backend API calls are made — all data is hardcoded in the component.
10. No pagination, search, sorting, filtering, download, export, or report detail functionality is included (out of scope).

## Non-Functional Requirements

- **Performance**: No external dependencies added. Page renders instantly with mock data. Table has only 5 rows — no virtualization needed.
- **Accessibility**: Table uses semantic `<table>`, `<thead>`, `<tbody>`, `<th>`, `<tr>`, `<td>` elements. Table has a descriptive caption or `aria-label`. Status badges convey meaning visually and are readable by screen readers. Page heading uses proper `<h1>` hierarchy.
- **Security**: No sensitive data handling. No `dangerouslySetInnerHTML`. No hardcoded secrets. All data is static strings (XSS-safe).
- **Browser Support**: Standard modern browser support (matching project baseline).

## Data/API Requirements

- **Data Models**: No external data models needed. Inline interface:
  ```typescript
  interface Report {
    reportName: string;
    type: string;
    generatedBy: string;
    generatedDate: string;
    status: 'Completed' | 'Pending' | 'Failed';
  }
  ```
- **API Endpoints**: None. This is frontend-only.
- **State Shape**: No component state needed. Mock data is a static constant array:
  ```typescript
  const mockReports: Report[] = [
    { reportName: 'Revenue Summary', type: 'Financial', generatedBy: 'John Doe', generatedDate: '2026-05-01', status: 'Completed' },
    { reportName: 'User Activity Report', type: 'Analytics', generatedBy: 'John Doe', generatedDate: '2026-05-02', status: 'Completed' },
    { reportName: 'Page Views Report', type: 'Traffic', generatedBy: 'John Doe', generatedDate: '2026-05-03', status: 'Pending' },
    { reportName: 'Session Report', type: 'Analytics', generatedBy: 'John Doe', generatedDate: '2026-05-04', status: 'Completed' },
    { reportName: 'Transaction Report', type: 'Financial', generatedBy: 'John Doe', generatedDate: '2026-05-05', status: 'Failed' },
  ];
  ```
- **Error Handling**: No network errors possible (no API calls). No loading states needed (data is static).

## UI/UX Requirements

- **Layout**:
  - Page title: "Reports" — matching `text-3xl font-bold tracking-tight text-white` pattern from `DashboardPage`
  - Subtitle: "View generated analytics reports" — matching `text-slate-400` pattern
  - Table container: `bg-slate-900/40 border border-slate-800 rounded-2xl` (matching DashboardPage card pattern)
  - Table wrapper with `overflow-x-auto` for responsive horizontal scrolling on small screens
- **Styling**: Tailwind CSS utility classes only. Dark theme palette consistent with existing pages.
  - Table header: `text-left text-xs font-medium text-slate-400 uppercase tracking-wider` with `border-b border-slate-800`
  - Table cells: `px-6 py-4 text-sm text-slate-200`
  - Table rows: `border-b border-slate-800` (except last row)
  - Alternating row background (optional): `hover:bg-slate-800/30` on row hover
- **Responsive Behavior**: Table container should scroll horizontally on mobile (`overflow-x-auto`). Use `max-w-full` to prevent overflow.
- **Interactions**:
  - Row hover: `hover:bg-slate-800/30 transition-colors` for visual feedback
- **Status Badges**:
  - Completed: `inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-medium bg-emerald-400/10 text-emerald-400`
  - Pending: `inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-medium bg-amber-400/10 text-amber-400`
  - Failed: `inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-medium bg-rose-400/10 text-rose-400`
- **Icons**: `FileText` or `BarChart3` (for page header area) from `lucide-react` — optional, only if consistent with other page patterns.

## Validation Rules

- No user input fields exist on this page — no validation rules apply.
- The table displays static mock data only.

## Edge Cases

1. **Empty mock data array** — If the `mockReports` array were empty, the table would render with headers but no rows. A simple "No reports available" empty state message could be shown below the header row (optional, not required by acceptance criteria).
2. **User is not authenticated** — `ProtectedRoute` redirects to `/login`.
3. **Narrow viewport (mobile)** — Table scrolls horizontally within its container. Column widths remain readable.
4. **Long report names** — Report names are short in mock data. If longer names appear in future, `truncate` class could be applied (not needed for current mock data).
5. **Date format consistency** — All dates use `YYYY-MM-DD` format. No localization needed for mock data.

## Assumptions

1. The Reports page route will be `/reports` (not nested under `/dashboard/reports`), consistent with how `/dashboard` and `/settings` are top-level protected routes.
2. The Reports NavItem in the sidebar will use an `onClick` handler with `useNavigate` to route to `/reports`, matching the pattern already established for the Settings NavItem in `DashboardLayout.tsx`.
3. The Reports page will be wrapped in `DashboardLayout` (same as DashboardPage and SettingsPage) so the sidebar and header remain visible.
4. The `ProtectedRoute` already wraps the route, so authentication gating is handled at the route level (per project gap #1 — auth is mock-level only).
5. No active/highlight state is needed for the Reports nav item beyond the existing `active` prop pattern. The Reports item will not be `active` by default since Overview is the default active item.
6. The table does not need sorting, filtering, or pagination — these are explicitly out of scope.
7. No loading state is needed since data is static and renders immediately.
8. The `NavItem` component in `DashboardLayout.tsx` already supports an optional `onClick` prop (established in TS-03), so the Reports NavItem can use the same pattern.

## Open Questions

1. **Should the Reports nav item show an active state when on `/reports`?** — Currently only "Overview" has `active` set to `true`. Should this be dynamic based on the current route? (Product/UX decision — same question as TS-03 Q1.)
2. **Should an empty state message be shown if the mock data array is empty?** — Not required by acceptance criteria, but good UX practice. (Implementation decision — spec does not require it.)
3. **Should the table include a "View Details" or action column?** — Explicitly out of scope per the story. Confirm no future expectation of action columns. (Product confirmation.)

## Implementation Plan

### Phase 1: Route Registration & Navigation Setup
1. Modify `src/components/DashboardLayout.tsx`:
   - The Reports `NavItem` currently has no `onClick` handler: `<NavItem icon={<BarChart3 size={20} />} label="Reports" />`.
   - Add an `onClick` prop to navigate to `/reports`: `onClick={() => navigate("/reports")}`.
   - Note: `useNavigate` is already imported in `DashboardLayout.tsx`. The `NavItem` component already accepts an optional `onClick` prop (established in TS-03).
2. Modify `src/App.tsx`:
   - Import `ReportsPage` from `./pages/ReportsPage`.
   - Add a new `<Route>` for `/reports` wrapped with `ProtectedRoute` and `DashboardLayout`, following the same pattern as `/dashboard` and `/settings`.

### Phase 2: Reports Page Component
1. Create `src/pages/ReportsPage.tsx`:
   - Component uses `React.FC` type annotation.
   - Define `Report` interface inline with fields: `reportName`, `type`, `generatedBy`, `generatedDate`, `status`.
   - Define `mockReports` constant array with the five specified records.
   - Define a `StatusBadge` helper component (co-located in the same file) that accepts a `status` prop and renders the appropriate styled badge.
   - Render structure:
     - Page header section with `<h1>` "Reports" and subtitle "View generated analytics reports".
     - Table container card (`bg-slate-900/40 border border-slate-800 rounded-2xl`).
     - Semantic HTML table with `<thead>` (column headers) and `<tbody>` (data rows).
     - Column headers: Report Name, Type, Generated By, Generated Date, Status.
     - Each row maps from `mockReports` array.
     - Status column uses `StatusBadge` component.
   - Keep file under ~150 lines (page component + helper should fit comfortably).

### Phase 3: Polish & Accessibility
1. Verify table uses semantic HTML elements (`<table>`, `<thead>`, `<tbody>`, `<th>`, `<tr>`, `<td>`).
2. Add `aria-label` or `<caption>` to the table for screen reader context.
3. Verify status badges are readable by screen readers (text content is sufficient; no `aria-label` needed since text is descriptive).
4. Verify horizontal scrolling works on narrow viewports.
5. Verify row hover states provide visual feedback.

### Phase 4: Testing
1. Write component tests for `ReportsPage` (when Vitest + React Testing Library is configured):
   - Renders heading "Reports" and subtitle "View generated analytics reports".
   - Renders exactly one table.
   - Table has correct column headers.
   - Table displays all 5 mock records with correct data.
   - Status badges display correct colors for each status type.
   - No charts, cards, filters, or extra widgets are rendered.
